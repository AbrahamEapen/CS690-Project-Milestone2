# Design doc S-3: Ranked applicants with a minimum flag

**S-3.** As an HR recruiter, I want all applicants for a posting listed by fit score, with anyone missing a required skill flagged "Does not meet minimum" and never ranked above an applicant who meets them all, so that I review qualified candidates first instead of reading every resume.

**Status:** open questions settled in Milestone 2 (§8); built in Milestone 2.

## 1. Problem
Screening 60 resumes to find 3 took two evenings (E-11), a keyword shortlist was mostly rejected (E-12), and mapping experience to requirements is the slowest step (E-13). Managers still advance candidates short on soft skills, so the system flags and never removes (E-14).

## 2. Scope
Rank a posting's applicants by required skills and fit score, with a flag and missing skills per entry, also over HTTP.

## 3. Non-goals
- No fit-score calculation (input from S-4), and no automatic rejection or removal (a proposal non-goal).
- No recruiter override of the flag (OQ-2, settled as D6), and no synonyms beyond `SKILL_SYNONYMS` (D7).
- No fit-score store from S-4: the ranking store (D5) is an in-memory stand-in that S-4 replaces.

## 4. Interface
`jobsboard.ranking`:
- `Candidate` (frozen dataclass): `application_id: str`, `skills: frozenset[str]`, `fit_score: int`.
- `RankedEntry` (frozen dataclass): `application_id: str`, `fit_score: int`, `meets_minimum: bool`, `flag: str | None`, `missing_required: tuple[str, ...]`.
- `rank_applicants(required_skills: frozenset[str], candidates: list[Candidate]) -> list[RankedEntry]`. It raises `InvalidFitScore(application_id, fit_score)`, `DuplicateApplication(application_id)`, or `InvalidSkill(skill)`.

`jobsboard.ranking_store` (the data module, D5):
- `RankingStore` with `set_requirements(posting_id, skills)`, `set_profile(application_id, skills, fit_score)`, and `candidates_for_posting(posting_id, applications) -> tuple[frozenset[str], list[Candidate]]`. It raises `PostingNotFound(posting_id)` when the posting has no requirements set.

HTTP: `GET /postings/{posting_id}/ranked` returns 200 with a list of `RankedEntry` as JSON (`flag` is `null` when absent), or 404 `{"detail": {"error": "posting_not_found"}}`. A posting with requirements but no eligible applications returns 200 with `[]`.

## 5. Data
- Every skill is non-empty after trimming; `required_skills` may be empty.
- Every skill is a `str`; anything else raises `InvalidSkill`.
- `fit_score` is a plain `int` from 0 to 100 inclusive. A `bool`, float, str or `None` raises `InvalidFitScore`.
- `missing_required`: each unmatched required skill's trimmed spelling, once, sorted by `(casefold(), spelling)`.

## 6. Rules
- **R1 (meets minimum; A-5).** `meets_minimum` is true exactly when `missing_required` is empty. Two skills match when they are equal after `strip()` and `casefold()`, or when both normalized forms are in the same `SKILL_SYNONYMS` group (D7). Matching works in both directions.
- **R2 (flag).** `flag` is `"Does not meet minimum"` exactly when `meets_minimum` is false, and `None` otherwise.
- **R3 (invariant).** No entry with `meets_minimum` false appears before an entry with `meets_minimum` true.
- **R4 (order).** Within each group, `fit_score` never increases from one entry to the next; entries with equal `fit_score` are in ascending `application_id` order (D2).
- **R5 (no one dropped).** The output contains each input `application_id` exactly once.
- **R6 (no side effects).** Ranking leaves the input list and every S-1 stage unchanged.
- **R7 (eligible applications; D8).** The ranked list for a posting contains exactly its applications that have a profile in the ranking store and are not at stage Rejected.

## 7. Edge cases
- No required skills (everyone meets the minimum), or every applicant flagged; an empty list.
- A flagged applicant scoring 100 against an unflagged one scoring 0 (R3).
- Skills that differ only in case or outer spaces (`" java "` vs `"Java"`); scores of −1 or 101.
- Synonyms in either direction (`"postgres"` meets `"PostgreSQL"`; `"PostgreSQL"` meets `"Postgres"`); a posting that requires both `"Postgres"` and `"PostgreSQL"` (one requirement, D7).
- Equal fit scores within a group (D2); an unknown posting (404); a posting whose every application is Rejected or unscored (`[]`).
- Non-`int` fit scores (`50.0`, `"50"`, `None`, `True`); a non-`str` skill.

## 8. Decisions (D) and open questions (OQ)
- D1. There is no Unicode normalization and no collapsing of inner spaces. Required skills that are equal after normalizing, or in the same synonym group (D7), count as one requirement. If such a requirement is missing, `missing_required` shows the posting spelling that sorts first by `(casefold(), spelling)`.
- D2 (settles OQ-1 / Q-6). Within each group, sort by `fit_score` descending, then by `application_id` ascending (plain string order). Source: team decision, 2026-11-11. Reason: it needs no data beyond `Candidate`, is deterministic, and does not depend on input order; no interviewee spoke to ties.
- D3. All input is validated before ranking, raising the first problem in list order. Exceptions subclass `ValueError` and keep their constructor arguments as attributes. Out-of-range scores are rejected, not clamped; duplicate IDs are exact string matches.
- D4 (revised in M2). `ranking.py` and `ranking_store.py` are new files in M2. The HTTP endpoint is built in M2 on FastAPI per `AGENTS.md`, reading from the ranking store (D5) and the S-1 `ApplicationStore`. No authentication (A-4), no pagination.
- D5. Skills, fit scores and posting requirements live in one in-memory data module, `jobsboard.ranking_store`, until S-4 builds the real score store. Starting the app with `JOBSBOARD_DEMO=1` seeds demo postings for "Try the story". Source: team decision, 2026-11-11 (the handout asks for one small data module the backend can replace).
- D6 (settles OQ-2 / Q-5). There is no recruiter override in S-3. The flag is computed only and never removes anyone (E-14). Override goes to the backlog as a later story. Source: team decision, 2026-11-11. Reason: INT-04:P06–P07 show managers advance borderline candidates, which the flag already allows, and an override would change R3 and need its own criteria.
- D7 (settles OQ-3 / Q-9). Synonyms match only through the fixed setting `SKILL_SYNONYMS`, which has two groups: {`postgres`, `postgresql`} and {`word`, `microsoft word`} (normalized forms). Membership is symmetric. Source: INT-03:P03 via Q-9 for the examples; team decision, 2026-11-11, to add no pairs without evidence.
- D8 (settles OQ-4). Applications with no profile (no fit score yet) or at stage Rejected are left out of the ranked list. The data module filters them before `rank_applicants` is called, so R5 still holds for the function's input. Source: team decision, 2026-11-11. Reason: an unscored application cannot be placed by R4, and a Rejected one needs no further review.
- D9 (gap check 2). `InvalidFitScore`, `DuplicateApplication` and `InvalidSkill` live in `ranking.py`, with the named settings below; `PostingNotFound` lives in `ranking_store.py`. Attribute names equal the constructor parameter names; no message format is required. `SKILL_SYNONYMS` is a public `tuple[frozenset[str], ...]` of normalized forms.
- D10 (gap check 2). Validation order: `required_skills` first in `sorted()` order, then each candidate in list order, checking duplicate ID, then fit score, then skills. Skills (required or candidate) are checked in two passes: first every non-`str` skill in `sorted(key=repr)` order, raising `InvalidSkill(raw)`; then every `str` skill that is blank after `strip()`, in `sorted()` order, also raising `InvalidSkill` (§5). Revised in M2 4a (team): plain `sorted()` raises `TypeError` on mixed types. `InvalidSkill.skill` is the raw value. `PostingNotFound` also subclasses `ValueError` (D3). Skills given as a single `str` instead of a collection of `str` (for example `set_profile(id, "Java", 50)`) raise `InvalidSkill` with that `str`, including the empty `str` `""`, because a `str` is itself an iterable of characters (team decision, M2 Task 5 review; `""` settled in Task 7). `application_id` is checked only for duplicates. Any iterable is accepted. A candidate with no skills is valid.
- D11 (gap check 2). `set_requirements(posting_id, skills)` and `set_profile(application_id, skills, fit_score)` take any iterable of skills, validate on set with the same errors as `rank_applicants`, and overwrite earlier values; an empty requirement set is allowed. `set_profile` checks `fit_score` before skills (the per-candidate order in D10). A set that raises leaves the store unchanged, so any earlier value for that posting or application is kept (team decisions, M2 Task 7). Profiles are keyed by `application_id` only. `candidates_for_posting` takes S-1 `Application` objects, keeps those with the given `posting_id`, a profile, and `stage is not Stage.REJECTED`, in the order given.
- D12 (gap check 2). `GET /postings/{posting_id}/ranked`: `posting_id` is any `str`; 404 exactly when no requirements are set for it. Stored data is always valid (D11), so ranking adds no other error status. JSON field names are the `RankedEntry` field names; `missing_required` is an array. `api.py` holds module-level `store` (S-1) and `ranking_store`.
- D13 (gap check 2). With `JOBSBOARD_DEMO=1` (exactly `"1"`), importing `api.py` calls `ranking_store.seed_demo(store, ranking_store)` once. It seeds one posting per S-3 AC with IDs starting `demo-` in both stores (rows in `docs/plans/S-3-plan.md`), plus `demo-empty`, which requires {Java} and has no applications, so `/ranked` shows the empty state `200 []` (§4; team decision, M2 Task 8). Demo applications get fixed, readable IDs (`demo-acN-x`) inserted through the private `ApplicationStore._put`, because S-1 has no public way to choose an ID; `pipeline.py` does not change (team decision, M2 4a). Outside the demo, data reaches the store only through Python calls until S-4.
